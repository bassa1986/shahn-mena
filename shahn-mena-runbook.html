Content & data-quality gaps

Incentives page shows no distinction between active and expired entries
app/incentives/page.tsx prints valid_until as plain text (صالح حتى: ...) with no comparison against today's date. Of the 10 hardcoded incentive rows seeded by scripts/scrapers/incentives-scraper.js, at least 5 carry a valid_until of 2025-12-31 or earlier — already in the past relative to current dates. They'll keep displaying as if still valid, with a past date, until someone either updates the rows or adds expiry logic to the page.
"Scrapers" for incentives and fuel prices are static hardcoded lists, not live scrapes
Despite the filenames, incentives-scraper.js and tco-scraper.js don't fetch anything from government or fuel-price sites — they push a fixed JS array (10 incentive rows; 3 country fuel/electricity rows for SA/AE/MA) into the DB every time they run. Only charging-scraper.js does a real live fetch, from the OpenChargeMap public API. This is fine as a v1, but "runs on a schedule" doesn't mean this data gets fresher over time — it means the same static numbers get re-written on schedule.
EV Models page is 6 hardcoded cards, not database-driven
app/models/page.tsx defines a static MODELS array (Lucid Air, BYD Seal, Tesla Model 3, Hyundai IONIQ 6, Kia EV6, MG4) with hardcoded specs, prices, and pros/cons directly in the component. Only the electricity/fuel price panel at the top of that page reads from the DB. Adding, removing, or re-pricing a model means editing and redeploying code, not updating data.
No path exists to review or publish new scraped articles
articles-generator.js inserts new articles with published: false and logs "Publish at: /admin/articles" — but app/admin, app/api/admin, and components/admin are all empty directories in the current codebase. There is no admin UI at all right now. The 10 articles currently live were inserted directly with a one-off Node script setting published: true manually, bypassing this pipeline entirely. If the Generate Articles workflow does start succeeding (see blocker above), its output will accumulate as unpublished drafts with no way to review or publish them short of writing SQL by hand against Neon.

Deliberate tradeoff worth knowing: articles-generator.js tries a local Ollama instance at localhost:11434 first, then falls back to Groq's API. On GitHub's hosted runners, Ollama will never be running, so every CI run wastes a few seconds on a connection attempt that's guaranteed to fail before it falls through to Groq. Harmless, but it means the workflow is fully dependent on GROQ_API_KEY being set as a GitHub Actions secret specifically — not a Vercel environment variable. Groq is never called by the deployed Next.js app itself; it's only used by this Node script. Setting GROQ_API_KEY in Vercel (as suggested earlier in this build) does nothing for this workflow.

System reference — environment variables

DATABASE_URL
Neon Postgres connection string. Read server-side only via dynamic import('@neondatabase/serverless') inside server components and Node scripts — never bundled to the client. Required for literally every page to render anything.
server-only
NEXT_PUBLIC_SITE_URL
Used in app/layout.tsx for metadataBase. Meant to be public, safe as-is.
public ok
GROQ_API_KEY / GROQ_MODEL
Used only by scripts/scrapers/articles-generator.js. Must be a GitHub Actions secret, not a Vercel variable — the deployed app never calls Groq.
CI secret only
OLLAMA_URL / OLLAMA_MODEL
Local-machine-only fallback for the same article generator script. Meaningless in CI or Vercel; only relevant if you run the scraper on your own PC with Ollama installed.
local-only
ADMIN_PASSWORD / ADMIN_JWT_SECRET
Referenced only by the currently-orphaned lib/auth.ts. Not required for the site to function today. Confirm these are not set in Vercel to avoid dangling unused secrets, unless you're actively finishing the admin dashboard.
unused currently
Local vs. production, as this specific setup actually differs:
  • Local dev reads secrets from .env.local (gitignored); Vercel reads from its own dashboard-configured env vars — these are two separate stores you must update independently, e.g. after rotating the DB password.
  • middleware.ts only blocks /admin/* when NODE_ENV === 'production'. Locally with npm run dev, that block doesn't apply — moot today since no admin pages exist, but worth remembering if the admin dashboard gets built later.
  • GitHub Actions runs on Node 20 (explicitly pinned in the workflow files after Node 24 became the runner default and broke setup-node's caching step). Vercel manages its own Node runtime separately — the two are not linked and don't need to match.
